# 第二轮复用：模板统一文件引用与清理锁

2026-10-29。承接[首轮复用审计](REUSE_COST_AUDIT.md)，本轮仅提炼文件引用/清理的共用协议，事务接入和前端上传仍是后续候选。最终运行身份见[证据](core-evidence/file-lifecycle-reuse.json)。

## 改动归属

模板新增FileLifecycleGuard，引用创建、更新、批量创建先锁本地元数据；清理锁定相同记录后重新检查年龄、当前路径及引用。引用批次按文件主键排序并去重，清理按主键顺序处理。清理使用独立READ_COMMITTED事务，避免空引用查询的间隙锁影响其他文件的关联；不符合事务要求的直接调用会拒绝。

FileReferenceService保留受支持API和外部URL原有行为，本地文件在清理先完成后不能创建悬空引用。批量创建原来把business_type和file_url参数颠倒，本轮在追踪同一写入链时确认并修复，已有单元回归。调用方仍须按模板约定使用规范本地URL，不得通过低级IService.save或任意SQL绕过协议。

食谱adaptations.py和工单build.py删除了清理SQL注入；改为检查模板具有共享能力，缺失时在业务适配之前停止。清理器直接来自显式模板，生成副本中的清理器、引用服务和锁组件应与模板逐文件一致。

业务权限、当前用户、私有文件访问、单封面/多图/历史记录的关联语义、主记录与引用共同事务不迁入通用组件。文件系统与数据库没有分布式原子提交保证，不能将本轮并发保护说成消除了所有磁盘/数据库失败模式。

## 有效测试

真实MySQL使用独立库file_lifecycle_test、新容器、新卷、回环随机端口和临时凭据。7个数据库场景包括：

1. 引用事务先持锁、清理看到旧候选后等待，引用提交后清理保留物理文件。
2. 清理先持锁并删除，关联等待后被拒绝，不产生悬空引用。
3. 锁后重新检查年龄及存储路径。
4. 反向输入批次使用同一主键锁序。
5. 非事务调用被拒绝。
6. 清理一个文件不以间隙锁阻塞另一个文件的关联。
7. 不符合清理隔离级别的调用被拒绝。

竞争测试通过performance_schema.data_lock_waits确认真实InnoDB等待，不用线程时间差代替数据库竞争。另有2项批量引用映射/外部URL回归。普通Maven没有专用数据库环境时会跳过这7项；本轮另行启用全部数据库场景，不能把跳过当通过。专用库的测试会重建两张测试表，不能接入平台数据库。
