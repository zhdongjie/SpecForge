## 复用差距与职责

| 能力 | 实际实现与重复 | 归属/本轮决定 |
| --- | --- | --- |
| 登录、当前身份、按钮权限 | 两项目均调用模板SecurityUtils、useAuthorities；grant只是各自业务权限前缀 | 模板已有能力继续直接复用，不另建权限库 |
| 数据归属/角色组合 | 食谱已发布/作者/审核人与工单报修人/当前维修人/全量查询有不同语义 | 留业务，不能只因方法都叫readable就合并 |
| 真实图片内容校验 | 两份ImageIO、MIME、大小/尺寸、文件名逻辑重复，工单缺少显式最小尺寸检查 | 本轮提炼为模板ImageValidationService，两项目改用相同校验 |
| 公开/私有存储 | 食谱复用FileManager和公开封面URL；工单独立卷、元数据与鉴权字节输出 | 保留差异，不用一个公开URL接口掩盖私有访问需求 |
| 文件引用和关联回滚 | 已共用FileReferenceService；单封面更新与多图/不可变历史记录的映射不同 | 复用已有服务，关联语义留项目；没有重复实现整套引用服务 |
| 清理并发保护 | 食谱adaptations.py和工单build.py都补文件行锁后重查引用 | 明确的后续模板候选；本轮不同时改清理事务行为 |
| 事务接入 | 都从模板MyBatis数据源、事务管理器创建JdbcTemplate/TransactionTemplate | 小型模板支持能力候选，先保留已通过回滚验收的实现 |
| 状态操作 | 发布/审核/收藏与分派/维修/验收不同；共有修订号和事务概念 | 不建立覆盖所有领域的Python状态引擎，避免核心膨胀 |
| 前端表单与详情 | 已共用Vuetify、ConfirmDialog、主题、请求和setBackendErrors；字段及布局是业务内容 | 保持模板风格约束；没有把整张表单复制进核心通用配置 |
| 上传前端与预览 | 食谱公开URL、工单认证Blob和释放ObjectURL不同 | 先保留；可进一步审计公共上传控件，但不能丢失私有预览边界 |
| 生成/交付包装 | 工单有明确重放脚本及Windows包装，部分运输代码重复 | 后续开发工具候选，不把工单流程变成核心运行时 |

## 本轮实现

模板新增ImageValidationService：调用现有FileUtils进行真实MIME检测，按调用方显式Policy校验大小、文件名、边长、解码及解码器/MIME一致性，返回已验证字节/MIME/名称。不存文件、不授予权限、不生成公开URL、不更新引用。

食谱仍在publish授权后调用FileManager；工单仍在submit/work授权后写私有卷。所有归属校验、引用事务、清理、状态、页面和部署规则保留。不存在按字段名自动识别业务或把工单搬进SpecForge核心。

接入先要求模板具有该能力；缺失时明确停止，不在生成器或项目内偷偷复制实现。旧发布模板不包含该新服务，需显式使用本轮模板提交。模板修改先独立验证并提交，再冻结为两个生成运行的输入；生成阶段不修改模板源。

## 需要保留的边界

- 规格仍只表达已支持的基础结构；复杂业务仍需明确项目实现。
- 此服务不是完整附件组件，也不是私有存储服务。既有FileManager元数据策略仍须单独执行。
- 清理锁、事务接入和前端上传是候选项，尚未在本轮提炼，不能标为完成。
- 本轮不改数据库结构与UI资产；仍重跑原功能/API/浏览器/独立部署验收，证明代码复用未改变交付行为。
- 三个仓库的变更为本地提交，没有发布新版或改写原发布标签。
